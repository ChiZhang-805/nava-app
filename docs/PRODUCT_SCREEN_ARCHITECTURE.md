# NAVA 产品页面架构与视觉方向

> 状态：第一阶段权威页面地图
> 适用范围：iPhone 首版、后续 Apple Watch/HealthKit 接入、SwiftUI 原生重写
> 目标：在生成逐页视觉稿和编写 SwiftUI 页面前，先固定产品信息架构、页面职责、状态和视觉语法。

## 1. 本文解决什么问题

NAVA 不能继续以“一个圆角矩形接一个圆角矩形”的方式扩展。统一设计系统不等于所有页面采用同一种卡片模板。本文把当前 React/Capacitor 版本、已开始的 SwiftUI 原生骨架、Supabase 数据能力和未来产品方向合并成一套完整页面地图，并为每条业务线指定不同的视觉语言。

本文是第二阶段逐页视觉稿的输入，不是最终像素稿。任何视觉稿或 SwiftUI 实现如果没有对应本文中的页面编号、状态和入口，都应先补充页面架构，而不是临时新增页面。

## 2. 代码盘点结论

### 2.0 第一版继承原则

本文中的“重设计”以当前 NAVA 第一版为起点，不以外部参考 App 为起点。五个主入口、中央 NAVA、首页小猫场景、两项顶栏指标、固定六模块、三套皮肤、记录/对话/回顾/我的功能树均属于产品合同。外部参考图只用于学习照片主导、横向浏览、数据标注、非规则图形和信息层级，不能替换 NAVA 的导航与功能。

第二阶段正式视觉稿必须为每页列出：第一版保留项、升级项、滚动类型、底栏状态、安全区、键盘状态和 SwiftUI 实现构件。未完成这组对照的图片只能算探索稿，不能进入代码实现。

### 2.1 当前已经存在的能力

- 五个主导航：今日、记录、NAVA、回顾、我的。
- 六个健康模块：睡眠、运动、饮食、情绪、专注、面部。
- 登录、注册、验证码、找回密码、首次引导和冷启动体验。
- 首页六模块、日历、今日安排、通知、提醒和组件排序。
- AI 文本/语音/图片/文件会话、历史、结构化记录确认。
- 周报、月度回顾、模块趋势、分享卡片和数据导出。
- 成长任务、积分、商城、购物车、卡片皮肤和小猫衣橱。
- 个人资料、账号安全、隐私数据、HealthKit 和 Apple Watch 连接。
- 原生餐食扫描的拍摄、菜品理解、身份确认、AI 盘装图生成、质量检查和核对骨架。

### 2.2 当前 SwiftUI 迁移状态

SwiftUI 已具备主导航、模块导航、基础设计令牌和餐食扫描先行流程；个人资料、账号安全、健康连接等仍有占位页。React 版本中的真实数据访问、状态管理和多数业务逻辑应迁移复用，不应把 SwiftUI 占位页误认为功能已经完成。

### 2.3 状态标记

| 标记 | 含义 |
| --- | --- |
| `现有` | React 版本已有主要交互或真实数据逻辑，SwiftUI 需要迁移 |
| `先行` | SwiftUI 已经有可运行骨架或部分原生流程 |
| `补全` | 当前仅有零散入口、弹层或能力，需要组成完整流程 |
| `新增` | 面向长期产品必须增加，目前代码中没有完整页面 |

## 3. 全局信息架构

### 3.1 五个主导航

1. **今日**：当天节律、六模块摘要、下一步建议和快速记录。
2. **记录**：六类数据记录入口、日期切换、补录与记录历史。
3. **NAVA**：AI 陪伴、语音对话、图片/文件理解和结构化动作确认。
4. **回顾**：跨模块趋势、周/月叙事报告、单指标深挖和分享。
5. **我的**：资料、连接、隐私、安全、主题、奖励和设备管理。

底部栏只承担一级导航。拍摄、专注计时、语音通话等沉浸任务进入独立全屏流程；设置和详情采用 NavigationStack；编辑或确认采用 sheet；轻量选项采用 confirmation dialog 或小型 popover。

### 3.2 滚动类型

| 类型 | 规则 | 适用页面 |
| --- | --- | --- |
| `F` 固定一屏 | 内容必须在可用高度内自适应；禁止纵向拖动和回弹 | 登录、权限说明、拍摄、专注计时、语音通话、单次完成页 |
| `A` 自适应一屏 | 常规机型一屏；紧凑高度或大字体时才允许滚动 | 首页、记录总览、部分确认页 |
| `V` 纵向内容流 | 内容天然超过一屏；底部操作使用安全区 inset，不覆盖内容 | 历史、报告、设置、商城、长表单 |
| `H` 横向分页 | 明确的同级对象浏览；使用吸附、页码和局部露出提示 | 餐次、趋势卡、奖励、服装、报告摘要 |
| `I` 沉浸式 | 全屏任务，不显示普通底栏；仅保留退出、状态和核心操作 | 相机、语音、专注、运动中 |

禁止同方向嵌套滚动。纵向页面中可以有横向分页区域，但必须让用户看得出可以横滑。内容不足一屏时不能为了“手感”保留空白滚动区域。

## 5. 必须设计的状态，不额外制造“空白页面”

每个页面族在第二阶段至少覆盖以下适用状态：

1. 首次空态：说明价值并提供一个主要动作。
2. 有数据态：真实内容优先，避免装饰占据大部分首屏。
3. 加载态：保留原页面骨架或按钮内进度，不进入独立加载页。
4. 失败态：在原位置显示原因、重试和手动替代路径。
5. 离线态：保留本地可用内容与未同步标识。
6. 权限未授予/拒绝：解释用途、提供系统设置入口，不反复弹系统框。
7. 低置信度：标注需要用户核对的字段，不把推测写成事实。
8. 键盘态：焦点输入始终可见，完成后恢复原缩放与布局。
9. 大字体态：支持 Dynamic Type；必要时从一屏切换为纵向内容流。
10. 减少动态效果：用淡入淡出替代扫描、弹簧和视差动画。
11. 极小/极大机型：iPhone SE 宽高与大屏 iPhone 都不出现横向溢出。
12. 系统中断：来电、动态岛活动、切后台、相机/麦克风被抢占后可恢复。

## 7. 非矩形视觉的实现方式

不需要依赖来源不明的下载图片来完成花瓣、弧线和不规则分区。

- **花瓣、扇区、能量弧**：使用 SwiftUI `Shape`、`InsettableShape` 和 `Canvas`，按数据参数计算 Bézier 路径；同一组件可生成宽窄不同但几何一致的花瓣。
- **扫描锚点与标注线**：使用 `Canvas` 或 overlay 中的 `Path`，锚点来自识别结果的归一化坐标。
- **趋势图与区间带**：使用 Swift Charts；图表与文字叙事共用语义颜色和辅助功能标签。
- **横向浏览**：使用 `ScrollView(.horizontal)` 与分页对齐，必须显示下一项局部或 page indicator。
- **连续状态动画**：优先使用 `PhaseAnimator`、`KeyframeAnimator`、`matchedGeometryEffect` 和明确的状态机；不为等待创建独立加载页。
- **图标**：优先 SF Symbols；品牌小猫、食物和衣物使用自有资产。第三方组件只在许可证、可访问性和长期维护均明确时采用。
- **AI 食物图**：国内模型负责菜品理解后的标准盘装图生成；后端继续做透明通道、尺寸、盘子占比、一致性、内容安全和缓存校验，客户端只展示通过质量门槛的资产。

## 9. 代码实现顺序

1. 固定 SwiftUI 设计令牌：颜色、字号、间距、安全区、动态字体和动效等级。
2. 建立导航和页面状态模型；禁止用多个布尔值拼装不可预测的弹层。
3. 实现通用基础设施：全屏/自适应/纵向/横向/沉浸五种页面容器。
4. 实现非矩形图形组件、图表语义和媒体/相机状态机。
5. 按流程迁移：账户 → 今日 → 六模块 → AI → 回顾 → 我的/奖励。
6. 每个页面完成后在紧凑、标准和大屏 iPhone 上验证；再验证键盘、Dynamic Type、VoiceOver、减少动态效果、横竖屏策略和系统中断。
7. 只有视觉、交互、真实数据和异常态均通过，才替换对应 React 页面。

## 10. 验收原则

- 页面之间共享品牌、排版和行为，不共享单一布局模板。
- 首屏只突出当前任务；次要能力渐进披露。
- 满屏背景可以延伸到安全区下方，交互控件必须遵守安全区。
- 固定一屏页面不产生底部白边、纵向回弹或虚假滚动条。
- 每个可点元素至少具备舒适触控区域和明确可访问名称。
- 数据图不只依赖颜色；图形、文字、数值和辅助功能描述共同表达。
- AI 推测、真实记录、设备同步和演示数据必须在视觉与数据合同上可区分。
- 不用独立纯色页、完成页或加载页掩盖导航和状态管理问题。
