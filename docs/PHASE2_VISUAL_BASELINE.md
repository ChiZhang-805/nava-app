## 0. 第一版是新版的产品合同

新版不是另做一套健康 App，也不是把参考图中的食物产品换成蓝色。第一版已经验证的页面关系、品牌记忆和操作习惯必须保留；第二阶段只重新组织视觉层级、信息密度、滚动边界和局部表达。

### 0.2 第一版需要修正，而不是继承的缺点

- 同一种大圆角矩形被用于过多页面，模块之间缺少形态与内容差异。
- 部分页面固定高度、内容高度与系统安全区共同造成底部空白、越界或虚假滚动。
- 首页、记录、回顾和我的在某些尺寸上信息密度失衡：不是简单放大或缩小，而是需要重新分配主次区域。
- 键盘出现时曾发生 WebView 自动缩放、控件被遮挡及关闭后无法复位；SwiftUI 实现必须由系统安全区和键盘避让管理。
- 弹层、菜单与底栏偶有同时抢占空间；新版规定同一时刻只允许一个主要覆盖层。
- 纯色过渡页、独立加载页和无内容完成页不再作为常规流程节点；进度和成功反馈留在原任务上下文中。

### 0.3 参考图的正确用途

参考图只贡献可复用的“表达语法”，不贡献 NAVA 的产品骨架：

- 非规则分段弧：用于饮食能量、节律完成度等真正具有比例/进度的数据；
- 照片锚点与细线标注：只用于食物、面部或其他图像理解结果；
- 花瓣/扇区：只用于食材构成等部分—整体关系；
- 横向卡带：只用于同级餐次、历史、奖励、报告章节，不承担一级导航；
- 大图主视觉：只在内容本身有照片或生成资产时使用，不给睡眠、设置等页面虚构摄影图；
- 不对称布局：用来强调主指标和下一步行动，而不是无目的地制造装饰。

## 1. 方向

NAVA 的视觉复杂度来自内容、摄影、排版、信息层级和少量有意义的数据图形，不来自“AI 科技感”。以下表现不得成为页面成立的前提：

- 霓虹发光、星空、山水、全屏光带、全息网格或复杂 3D 场景；
- 需要 shader 才能接近视觉稿的背景和控件；
- 用大量透明玻璃、渐变和发光边框掩盖普通信息架构；
- 为了显得智能而添加与任务无关的扫描线、光圈和 AI 符号；
- 将所有内容都装进相同圆角矩形卡片。

页面应采用雾白或非常浅的暖灰底色、深海军蓝文字、克制的 NAVA 蓝，以及少量杏橙、薰衣草色作为数据语义色。真实照片、食物盘装图和小猫资产可以成为视觉主角；布局本身不得依赖不可重复的生成纹理。

## 2. 可实现性门槛

视觉稿中的结构必须能够由以下 SwiftUI 基础能力直接复现：

- `VStack`、`HStack`、`ZStack`、`Grid`；
- 纵向/横向 `ScrollView`、`TabView`；
- 普通图片遮罩、`SF Symbols` 和项目自有小猫资产；
- 简单 `Shape` / `Path`、重复的圆角线段、花瓣和进度弧；
- Swift Charts 的折线、区间、热力格和雷达数据的自定义 `Shape`；
- 原生相机预览、细线标注、标准 sheet、菜单、按钮和键盘。

如果一张稿件不能说明它由哪些基础构件组成，不能进入代码实现阶段。

### 3.1 底栏合同

- 五个入口顺序、中央 NAVA 权重和圆形选中语义保持不变。
- 底栏固定在 `safeAreaInset(edge: .bottom)`，页面内容的底部内边距由底栏实际高度统一提供，禁止每页手写一套空白。
- 今日、记录总览、回顾、我的总览显示底栏；NAVA 当前第一版语义继续采用独立对话界面。
- 记录编辑/详情、相机、语音、专注、运动中、个人中心子页隐藏底栏，以返回导航恢复上下文。
- 中央按钮不得覆盖最后一行内容；在 360×740 至 430×932 范围内保持至少 44 pt 触控区。

### 3.2 滚动合同

| 类别 | 行为 | 典型页面 |
| --- | --- | --- |
| 固定一屏 | 不创建 `ScrollView`，内容使用可用高度和安全区约束；禁止拖出纯色底 | 相机、实时语音、专注计时、短确认、常规尺寸首页 |
| 自适应一屏 | 标准字号不滚动；紧凑高度/大字号时整体退化为一个纵向滚动容器 | 登录、记录总览、情绪签到、计划页 |
| 内容流 | 只允许一个主纵向 `ScrollView`；底部操作通过 `safeAreaInset` 固定或随内容排列 | 报告、历史、我的总览、隐私、长表单 |
| 横向同级浏览 | 使用可见的下一项边缘、分页位置或标题提示；不得与系统返回手势冲突 | 餐次、周报章节、奖励、衣橱 |
| 沉浸任务 | 隐藏普通底栏，只保留退出、状态和核心操作；系统中断后可恢复 | 拍摄、语音、专注、运动中 |

页面是否滚动由视觉规格表预先标记，不由实现者根据“看起来放不下”临时添加。内容少于一屏时不得保留回弹和底部空白；内容超出时不得用缩小字体、压扁触控区或截断代替滚动。

### 3.4 第一版记录流程的状态继承

六个模块都已经具备 `entry / writing / recap / celebrate` 等状态和四档尺寸截图。重设计不得只画每条业务线的“首页”，必须逐状态继承其功能：

| 状态 | 保留职责 | 新版处理 |
| --- | --- | --- |
| `entry` | 选择记录入口、理解当前状态、进入任务 | 短任务优先一屏；只显示当前最重要的一步，不用六张入口卡 |
| `writing` | 输入、选择、拍摄或设备同步 | 键盘/相机/选择器成为唯一主要交互；底栏隐藏；字段有明确来源与单位 |
| `recap` | 核对本次记录和保存内容 | 摘要与可编辑证据相邻；低置信字段可修改；不得静默写入 |
| `celebrate` | 轻量成功反馈与回到上下文 | 采用原页面 overlay/状态变化；不再出现独立纯色完成页或强制加载页 |

每条业务线的视觉可以不同，但导航恢复、返回行为、数据来源和失败恢复必须一致。饮食可使用照片和盘装图，睡眠使用时间河流，情绪使用连续强度和身体感受，运动使用轨迹和指标，专注使用时间与中断刻痕，面部使用明示同意与图像质量标记；不能再用同一套圆角卡模板只替换图标和标题。

### 3.5 四档 iPhone 的内容密度合同

适配不是把 390 pt 宽的画面等比缩放，也不是为每台手机另画一套固定像素稿。页面先保证系统安全区、可读字号和 44 pt 触控区，再按可用高度调整装饰留白、模块编排和滚动状态。

| 参考可用尺寸 | 布局策略 | 禁止做法 |
| --- | --- | --- |
| 360×740 紧凑 | 页边距 14–16 pt；先压缩背景舞台和区块间距；同级摘要允许横向分页；一屏合同无法成立时切换为一个纵向滚动 | 缩小正文、压扁按钮、隐藏必要字段、整页 `scaleEffect` |

### 3.6 第二阶段的重点重设计顺序

首页当前结构与品牌识别已经成立，第一批正式稿只做比例、对比度、紧凑机型和编辑态校准。主要重设计投入按以下顺序进行：

#### 3.6.1 第二个底栏入口：数据与记录总览

- 它不是六个“去填写”的同形按钮，而是“今天六类数据是否完整、最近发生了什么、下一条最值得记录什么”的总览。
- 顶部保留日期切换，但采用轻量日期带；左右滑切换相邻日期，点击日期打开日历，避免把日期功能藏进菜单。
- 首屏主区域按信息价值而非固定 2×3 卡片编排：一个今日节律总览、两个需要注意的模块、其余模块的紧凑状态带。
- 六模块始终可一键进入；已记录显示关键数值和更新时间，未记录显示明确动作，低置信/待确认显示证据状态。
- 横向滑动只用于同级日期或模块摘要；详情内容仍只有一个纵向滚动所有者。
- 高频入口直接可见：快速记录、补录昨日、查看报告；筛选、导出等低频动作才进入更多菜单。

#### 3.6.2 任务/成长页

- 保留积分、任务与成长奖励，但从白卡长列表升级为“今日路径 + 本周进度 + 可选挑战”。
- 今日路径用纵向进度线表达已完成、当前和下一步；每个任务行显示动作、预计用时和奖励，不需要再次打开菜单才能开始。
- 本周进度采用横向分页，允许左右滑浏览不同主题；页面纵向滚动只承载章节，不嵌套第二个纵向任务列表。
- 顶部只显示积分和连续完成天数；商城入口作为明确按钮，不与健康任务混在右上角下拉菜单。
- 完成反馈留在当前任务行，并让下一任务自然上移；不跳到纯色成功页。

#### 3.6.3 日历与快捷记录入口

- 日历是记录系统的时间索引，不是孤立子页。第二个底栏入口的日期带、首页快捷入口和报告页日期都能直接进入同一个日历上下文。
- 月视图用颜色/填充表达六模块完整度，选中一天后在同页下方显示当日摘要；点击摘要进入单日记录。
- 长按日期或点击固定“快速记录”操作，直接弹出六模块快捷选择；不先经过菜单或加载页。
- 对高频记录提供最近使用和上下文建议，例如晚间优先睡眠/情绪、运动后优先运动恢复；建议只排序入口，不自动提交数据。
- 月份横向切换、当日摘要纵向滚动；二者手势区域分开，避免与系统返回冲突。

#### 3.6.4 NAVA 对话页

- 保留第一版独立对话、历史、多模态、语音和小猫状态；不套普通底栏，也不把所有操作塞进右上角菜单。
- 标题区直接提供会话标题与历史入口；输入器直接提供照片/相机、文件、文本、语音，长按主语音动作进入连续倾听。
- 与健康记录有关的快捷动作以可横向滑动的上下文建议带出现，例如“总结今天”“补记睡眠”“分析这餐”；用户开始输入后自动收起。
- 消息流按文本、图像分析、报告和数据写入确认使用不同版式；数据写入确认必须在消息上下文内显示字段差异。
- 右上角菜单只保留低频会话操作，如重命名、导出、清空；停止生成、重新生成、复制、反馈等操作贴近对应消息。
- 键盘出现时只调整消息区和输入器，标题不被放大，关闭键盘后恢复原位置；语音沉浸态不产生页面滚动。

这四组页面完成后，再扩展个人中心、商城和其余工具页。正式视觉稿必须同时画出默认态、内容较多态、空/缺失态及至少一个交互展开态，不能只画一张静态首页。

- 食物照片和标准盘装图属于内容资产，不承担布局结构。
- 12 张基准稿通过后，才扩展其余常规态、空态、权限、键盘、错误和系统中断画面。
- 与第一版逐页对照：入口、功能、数据、底栏语义、小猫和场景没有被参考图误删。
- 视觉稿中的曲线、花瓣、弧段、图片标注和动效均有明确 SwiftUI 构件与数据来源；不能靠不可控生图生成 UI 本体。
- 每个页面都标注 `F/A/V/H/I` 滚动类型；没有未定义的嵌套滚动、底部空白或系统返回手势冲突。
- 360×740、375×812、390×844、430×932 四档尺寸分别验收，不使用整页等比缩放冒充适配。
- Dynamic Type、键盘、来电/动态岛状态、减少动态效果和高对比度均有对应状态稿或实现说明。

## 7. SwiftUI 实现映射

| 视觉需求 | 推荐实现 | 约束 |
| --- | --- | --- |
| 第一版五入口底栏 | `safeAreaInset` + 自定义 `Layout`/`HStack` + `matchedGeometryEffect` | 不使用固定屏幕坐标；中央 NAVA 只在可用区内抬升 |
| 首页固定六模块排序 | `LazyVGrid`/自定义 `Layout` + `draggable`/`dropDestination` | 数据永远六项；没有删除和添加状态 |
| 分段弧/不规则花瓣 | `Shape`、`Path` 或 `Canvas`，参数由真实比例驱动 | 先定义数据与无障碍文本，再绘制形状 |
| 图片锚点 | `GeometryReader` 将归一化坐标映射到图像 `aspectFit` 区域 | 坐标绑定内容区域，不绑定设备像素 |
| 内容型图表 | Swift Charts；特殊外形才用 `Canvas` | 图形必须提供文本摘要，未知数据不伪造 |
| 固定与可滚动页面 | `ViewThatFits`/尺寸判断选择一屏或单一 `ScrollView` | 不通过 `.scaleEffect` 缩放整页，不嵌套同向滚动 |
| 键盘与底部操作 | `safeAreaInset`、`FocusState`、系统键盘工具栏 | 输入字号保持系统可读尺寸，关闭键盘后布局自动恢复 |
| 小猫状态动画 | 现有分层资产 + `TimelineView`/关键帧动画 | 保持原形，不依赖每帧生图；支持减少动态效果 |
